# Evaluation orders: rulings taken while implementing the subnet side

Decisions on points `2026-10-01-evaluation-orders-design.md` leaves open, one per line.

## Held-out sets

Ruling: RL's prompt universe is the whole train split of every catalog source — `window_prompt_range` slices `[0, len(env))` and every runtime factory (`spec.create()`, `load_external_backend` default) builds the train split — so no train index range of any source is disjoint from RL; only another split is. A test pins both facts.
Ruling: math is `reliquary_dapo_math_v1`, split `eval`, not OpenMathInstruct at offset 10000 — the design's condition ("if the check confirms it is disjoint") fails: RL samples OMI's whole index space, the 2026-09-11 measurement found 218/500 (43.6 %) of the offset-10000 problems trained with identical content, and OMI-2 repeats each question ~20 times across rows, so index-disjoint is not content-disjoint. The DAPO package assigns problems to train/eval/qualification by a salted hash of the problem key; RL and corpus jobs build train only.
Ruling: logic is `reliquary_logic_v2`, split `eval` — splits interleave (position = index·3 + split), so no eval task is ever a train task, whatever index RL or the corpus job (rows 100M..100.05M) uses.
Ruling: instruction following is `reliquary_instruction_following_v1`, split `eval` (10 % of the corpus, by a salted hash of the row key) — the IF corpus job (0..20k) and RL use train only.
Ruling: code is `reliquary_code_v1` (the code corpus job's source, which the code corpus job uses), rows `[2,381,806, 2,481,806)`: the last 100,000 rows of the pinned curation (`d3caaefc`, 2,481,806 rows). The package has no other split. It is disjoint from every corpus job and `jobs create` (CLI and admin) now refuses a job reaching it; it is NOT disjoint from past RL, which sampled the whole train split. This is the one ruled exception (`RL_OVERLAP_RULED`), written into its `set.json`; excluding the range from RL sampling is a follow-up (a consensus change, out of scope). `build-set` refuses a source of another length than the one the range was chosen against.
Ruling: the prod corpus jobs are listed in one table (`CORPUS_RANGES`); a new prod job on a train split must be added there, and `jobs create` refuses any job reaching a held-out region regardless.
Ruling: a set is the first N of `random.Random(seed).sample(region, count)`, written in that order with problem ids `{set_id}-{ordinal:06d}`; an order of N problems takes the first N lines. Ids carry no source index.
Ruling: `grading.jsonl` holds `{problem_id, source, split, source_index, prompt_sha256}` — the grader re-reads the source row and refuses (`score=null`, `source_drift`) a row whose prompt is no longer the frozen one, rather than copying answers out of the source.
Ruling: the subnet bucket holds its own copy of `set.json` beside `grading.jsonl`, and the grader trusts that copy, never the platform's. Publishing is create-only: the same bytes again are a no-op, other bytes are refused (`SetConflict`).

## Runner

Ruling: completions are uploaded as several files, `completions-NNNNN.jsonl`, one per chunk of 64 problems, each through the multipart API; `completion_keys` lists them in order.
Ruling: resume is from the pod's work directory (`--work-dir`): a chunk with a key is skipped, a chunk written but not uploaded is sent as written (its sha256 is recorded), and an upload started is resumed by its `upload_id` with only the missing parts. A new pod (lost disk) starts over: the contract has no listing of a task's finished uploads.
Ruling: each problem gets its own vLLM seed, `sha256(f"{seed}:{problem_id}")[:4]`, so chunking and resume never change a sample.
Ruling: upload parts are numbered from 1 (`PART_BASE`), part n covering bytes `[(n-1)·part_size, n·part_size)`.
Ruling: lost contact is a 401/403/409/410 on a task call (no retry), or 4 heartbeats failing in a row; the work stops at the next chunk boundary (vLLM's batch is not interruptible). On one upload's own routes (`uploads/{id}`, its parts, `complete`) only 401/403 stop the pod: a 409/410 there means the upload is complete or gone, so the client reads the key from `GET uploads/{id}` when it carries one, else starts the upload again, once (review I5). 5xx, 429 and transport errors are retried 4 times with a growing backoff.
Ruling: `progress` events count problems (`done`, `total`); `model_loaded` carries `{vllm_version, gpu, model_sha, chat_template_sha256, seconds}`; `model_sha` is the commit Hugging Face served the snapshot at (its directory name), refused unless it is the pinned revision (review M3).
Ruling: prompts reach vLLM as token ids: the chat template's text is encoded without special tokens (the template holds its own BOS), raw text with them (review I4). `max_model_len` is the longest prompt plus `max_new_tokens` (review M2).
Ruling: an absent or null sampling field takes its default: temperature 1, top_p 1, no top-k, seed 0 (review M10).
Ruling: `top_k` 0 or null means no top-k (vLLM `-1`).

## Grading and report

Ruling: the grade body requires a `provenance` object with `model, revision, model_sha, sampling, thinking, max_new_tokens, vllm_version, gpu, pod_provider_id` (more keys allowed), recorded verbatim in `report.json` — the admin host knows none of them, and the pod provider id is the platform's alone (review M4).
Ruling: the grade body requires `samples_per_set` (samples ordered per problem, part of the request digest); a `sample_index` outside `[0, samples)` is rejected and counted `out_of_range_rows`, a repeat `duplicate_rows` (review I1).
Ruling: `correct` is `score >= 1.0`: for code's fractional reward a sample is correct only when every case passes; `mean_score` reports the fraction too. pass@k is computed on `correct`.
Ruling (review I2): the headline pass@1/pass@k count a missing or ungraded (`score=null`) sample as a failure, n = samples ordered; `excluding_ungraded_and_missing` gives the variant over graded samples only. Each env reports `expected_rows, graded_rows, ungraded_rows, missing_rows, complete`; the report and manifest carry a top-level `complete`. An env with no graded row stays in the macro at 0 and is named in `macro.envs_without_graded_rows`.
Ruling: instruction following is graded on the text after the last `</think>` (an unterminated `<think>` leaves nothing, a format failure) — its grader reads the whole completion and the catalog runs it without reasoning, but an order may ask for thinking. Other environments are graded on the whole completion, as RL does.
Ruling: a format failure is: no `\boxed{}` (math), no fenced block (code), no extractable JSON object (logic), an empty answer (IF).
Ruling: rows the order did not ask for (`unexpected_rows`), repeated `(problem_id, sample_index)` (`duplicate_rows`, first kept), out-of-range sample indices and unparseable lines (`malformed_rows`) are counted, never graded.
Ruling: the bootstrap resamples problems 2000 times with seed 0 (recorded in the report); the interval is the nearest-rank 2.5/97.5 percentiles (`ceil(q·R)`-th smallest, review M1) of the resampled means of per-problem c/n.
Ruling: idempotency is keyed by the eval id and the request digest (`set_ids`, `completion_keys`, `problems_per_set`, `samples_per_set`; provenance excluded): the same request answers 202 then 200 with the stored keys, another request under the same id is 409 `grade_exists_with_another_request`. A failed grading answers 500 once and the next call starts it again. Decisions are single-flight per eval id (an `asyncio.Lock`), so two first calls start one grading and the manifest hashes the bytes uploaded (review I6). The corpus export route has the same unlocked pattern on the base branch; it is left as is (its output is deterministic but for `created_at`) and noted here.
Ruling: evaluations are written under `evaluations/{eval_id}/` (`graded.parquet`, `report.json`, `manifest.json`), never `deliveries/`, so the corpus export route never reads or overwrites one (review I3).
Ruling: refusals the caller can act on are answered synchronously before any 202: 404 `set_unknown`, 422 for a bad key, a missing provenance key or a `problems_per_set`/`samples_per_set` out of range, 503 `code_sandbox_unavailable`; a completion key missing from the bucket fails the grading (500).
Ruling (review C1, fixed on the base branch fbdd3beb): code is never run by the package's own runner on the admin host. Every row is scored by `reward_scorer`, which for a materials source (`reliquary_code_v1`, `opencodeinstruct`) sends `admission_reward_cases` to the admission scorer and the runsc grading service (`--network=none`), exactly as admission does; `jobs export --apply-filter` and the delivery route use the same path. A host without the grading service refuses: the grade route answers 503 `code_sandbox_unavailable`, the delivery route ships the filter unapplied with its note, and a per-row service failure is `score=null` (`grader_error: GraderInfrastructureError`), never 0.
Ruling: rows are graded sequentially in a worker thread (the environment objects are not known to be thread-safe).
Ruling (review I7): disjointness follows source lineage (`SOURCE_LINEAGE`): `reliquary_code_v1` and `opencodeinstruct` are one curation with one index space, so a job on either is refused the held-out tail and RL on both is the ruled overlap. Sources of one corpus with different index spaces are taken to overlap. The code card and the report's `provenance.sets[]` carry `rl_disjointness` and a `contamination_note` (scores of Reliquary-trained models may be inflated); the others carry null. A content-hash check of the tail against the rest of the curation is not done (follow-up before selling code to Reliquary-trained models).

## Review minors left as they are

Ruling (M5): completion keys are checked syntactically, not bound to the order's task prefix — the platform signs every grade call and names its own keys; binding them needs a key layout the contract does not fix yet.
Ruling (M6): `format_failed` approximates each package's extractor (a closed fence, OMI's last-box parser), so a row can be a format failure with a score > 0; the rate is a diagnostic, the score is the grader's.
Ruling (M7): macro pass@k averages each env's own value; an env's pass@k may be over fewer problems (n ≥ k, said in `n_problems`); no macro CI.
Ruling (M8): grading is sequential and its progress in memory; an admin restart loses a running grading, and the next grade call starts it again (manifest last keeps it safe).
Ruling (M9): the platform's `set.json` carries `seed` and `index_range`, so anyone can recompute the source indices; the answers are public in the packages anyway. To revisit if a private source is ever used.

## v2: evaluations generated by SN81 miners

Ruling (user, 2026-10-01): no per-token pricing, no burn change, no pricing route, no `miner_alpha_per_window`, no pace controller. An eval job is paid exactly like a corpus/SFT job: a fixed cap share per task, split by verified tokens, settlement byte-identical to the base. The share defaults to 0.02, is set at job creation by the operator/platform and changed with the existing cap route; the criteria are to be decided with the user later. Per-token pricing is a possible later update. The design's "Incentive logic" section is replaced by a short "Incentives" section.
