# Evaluation orders: rulings taken while implementing the subnet side

Decisions on points `2026-10-01-evaluation-orders-design.md` leaves open, one per line.

## Held-out sets

Ruling: RL's prompt universe is the whole train split of every catalog source — `window_prompt_range` slices `[0, len(env))` and every runtime factory (`spec.create()`, `load_external_backend` default) builds the train split — so no train index range of any source is disjoint from RL; only another split is. A test pins both facts.
Ruling: math is `reliquary_dapo_math_v1`, split `eval`, not OpenMathInstruct at offset 10000 — the design's condition ("if the check confirms it is disjoint") fails: RL samples OMI's whole index space, the 2026-09-11 measurement found 218/500 (43.6 %) of the offset-10000 problems trained with identical content, and OMI-2 repeats each question ~20 times across rows, so index-disjoint is not content-disjoint. The DAPO package assigns problems to train/eval/qualification by a salted hash of the problem key; RL and corpus jobs build train only.
Ruling: logic is `reliquary_logic_v2`, split `eval` — splits interleave (position = index·3 + split), so no eval task is ever a train task, whatever index RL or the corpus job (rows 100M..100.05M) uses.
Ruling: instruction following is `reliquary_instruction_following_v1`, split `eval` (10 % of the corpus, by a salted hash of the row key) — the IF corpus job (0..20k) and RL use train only.
Ruling: code is `reliquary_code_v1` (the code corpus job's source, which the code corpus job uses), rows `[2,381,806, 2,481,806)`: the last 100,000 rows of the pinned curation (`d3caaefc`, 2,481,806 rows). The package has no other split. It is disjoint from every corpus job and `jobs create` (CLI and admin) now refuses a job reaching it; it is NOT disjoint from past RL, which sampled the whole train split. This is the one ruled exception (`RL_OVERLAP_RULED`), written into its `set.json`; excluding the range from RL sampling is a follow-up (a consensus change, out of scope). `build-set` refuses a source of another length than the one the range was chosen against.
Ruling: the prod corpus jobs are listed in one table (`CORPUS_RANGES`); a new prod job on a train split must be added there, and `jobs create` refuses any job reaching a held-out region regardless.
Ruling: a set is the first N of `random.Random(seed).sample(region, count)`, written in that order with problem ids `{set_id}-{ordinal:06d}`; an order of N problems takes the first N lines. Ids carry no source index.
Ruling: `grading.jsonl` holds `{problem_id, source, split, source_index, prompt_sha256}` — the grader re-reads the source row and refuses (`score=null`, `source_drift`) a row whose prompt is no longer the frozen one, rather than copying answers out of the source.
Ruling: the subnet bucket holds its own copy of `set.json` beside `grading.jsonl`, and the grader trusts that copy, never the platform's. Publishing is create-only: the same bytes again are a no-op, other bytes are refused (`SetConflict`).

## Runner

Ruling: completions are uploaded as several files, `completions-NNNNN.jsonl`, one per chunk of 64 problems, each through the multipart API; `completion_keys` lists them in order.
Ruling: resume is from the pod's work directory (`--work-dir`): a chunk with a key is skipped, a chunk written but not uploaded is sent as written (its sha256 is recorded), and an upload started is resumed by its `upload_id` with only the missing parts. A new pod (lost disk) starts over: the contract has no listing of a task's finished uploads.
Ruling: each problem gets its own vLLM seed, `sha256(f"{seed}:{problem_id}")[:4]`, so chunking and resume never change a sample.
Ruling: upload parts are numbered from 1 (`PART_BASE`), part n covering bytes `[(n-1)·part_size, n·part_size)`.
Ruling: lost contact is a 401/403/409/410 on a task call (no retry), or 4 heartbeats failing in a row; the work stops at the next chunk boundary (vLLM's batch is not interruptible). On one upload's own routes (`uploads/{id}`, its parts, `complete`) only 401/403 stop the pod: a 409/410 there means the upload is complete or gone, so the client reads the key from `GET uploads/{id}` when it carries one, else starts the upload again, once (review I5). 5xx, 429 and transport errors are retried 4 times with a growing backoff.
Ruling: `progress` events count problems (`done`, `total`); `model_loaded` carries `{vllm_version, gpu, model_sha, chat_template_sha256, seconds}`; `model_sha` is the commit Hugging Face served the snapshot at (its directory name), refused unless it is the pinned revision (review M3).
Ruling: prompts reach vLLM as token ids: the chat template's text is encoded without special tokens (the template holds its own BOS), raw text with them (review I4). `max_model_len` is the longest prompt plus `max_new_tokens` (review M2).
Ruling: an absent or null sampling field takes its default: temperature 1, top_p 1, no top-k, seed 0 (review M10).
Ruling: `top_k` 0 or null means no top-k (vLLM `-1`).

## Grading and report

Ruling: the grade body requires a `provenance` object with `model, revision, model_sha, sampling, thinking, max_new_tokens, vllm_version, gpu, pod_provider_id` (more keys allowed), recorded verbatim in `report.json` — the admin host knows none of them, and the pod provider id is the platform's alone (review M4).
Ruling: the grade body requires `samples_per_set` (samples ordered per problem, part of the request digest); a `sample_index` outside `[0, samples)` is rejected and counted `out_of_range_rows`, a repeat `duplicate_rows` (review I1).
Ruling: `correct` is `score >= 1.0`: for code's fractional reward a sample is correct only when every case passes; `mean_score` reports the fraction too. pass@k is computed on `correct`.
Ruling (review I2): the headline pass@1/pass@k count a missing or ungraded (`score=null`) sample as a failure, n = samples ordered; `excluding_ungraded_and_missing` gives the variant over graded samples only. Each env reports `expected_rows, graded_rows, ungraded_rows, missing_rows, complete`; the report and manifest carry a top-level `complete`. An env with no graded row stays in the macro at 0 and is named in `macro.envs_without_graded_rows`.
Ruling: instruction following is graded on the text after the last `</think>` (an unterminated `<think>` leaves nothing, a format failure) — its grader reads the whole completion and the catalog runs it without reasoning, but an order may ask for thinking. Other environments are graded on the whole completion, as RL does.
Ruling: a format failure is: no `\boxed{}` (math), no fenced block (code), no extractable JSON object (logic), an empty answer (IF).
Ruling: rows the order did not ask for (`unexpected_rows`), repeated `(problem_id, sample_index)` (`duplicate_rows`, first kept), out-of-range sample indices and unparseable lines (`malformed_rows`) are counted, never graded.
Ruling: the bootstrap resamples problems 2000 times with seed 0 (recorded in the report); the interval is the nearest-rank 2.5/97.5 percentiles (`ceil(q·R)`-th smallest, review M1) of the resampled means of per-problem c/n.
Ruling: idempotency is keyed by the eval id and the request digest (`set_ids`, `completion_keys`, `problems_per_set`, `samples_per_set`; provenance excluded): the same request answers 202 then 200 with the stored keys, another request under the same id is 409 `grade_exists_with_another_request`. A failed grading answers 500 once and the next call starts it again. Decisions are single-flight per eval id (an `asyncio.Lock`), so two first calls start one grading and the manifest hashes the bytes uploaded (review I6). The corpus export route has the same unlocked pattern on the base branch; it is left as is (its output is deterministic but for `created_at`) and noted here.
Ruling: evaluations are written under `evaluations/{eval_id}/` (`graded.parquet`, `report.json`, `manifest.json`), never `deliveries/`, so the corpus export route never reads or overwrites one (review I3).
Ruling: refusals the caller can act on are answered synchronously before any 202: 404 `set_unknown`, 422 for a bad key, a missing provenance key or a `problems_per_set`/`samples_per_set` out of range, 503 `code_sandbox_unavailable`; a completion key missing from the bucket fails the grading (500).
Ruling (review C1, fixed on the base branch fbdd3beb): code is never run by the package's own runner on the admin host. Every row is scored by `reward_scorer`, which for a materials source (`reliquary_code_v1`, `opencodeinstruct`) sends `admission_reward_cases` to the admission scorer and the runsc grading service (`--network=none`), exactly as admission does; `jobs export --apply-filter` and the delivery route use the same path. A host without the grading service refuses: the grade route answers 503 `code_sandbox_unavailable`, the delivery route ships the filter unapplied with its note, and a per-row service failure is `score=null` (`grader_error: GraderInfrastructureError`), never 0.
Ruling: rows are graded sequentially in a worker thread (the environment objects are not known to be thread-safe).
Ruling (review I7): disjointness follows source lineage (`SOURCE_LINEAGE`): `reliquary_code_v1` and `opencodeinstruct` are one curation with one index space, so a job on either is refused the held-out tail and RL on both is the ruled overlap. Sources of one corpus with different index spaces are taken to overlap. The code card and the report's `provenance.sets[]` carry `rl_disjointness` and a `contamination_note` (scores of Reliquary-trained models may be inflated); the others carry null. A content-hash check of the tail against the rest of the curation is not done (follow-up before selling code to Reliquary-trained models).

## Review minors left as they are

Ruling (M5): completion keys are checked syntactically, not bound to the order's task prefix — the platform signs every grade call and names its own keys; binding them needs a key layout the contract does not fix yet.
Ruling (M6): `format_failed` approximates each package's extractor (a closed fence, OMI's last-box parser), so a row can be a format failure with a score > 0; the rate is a diagnostic, the score is the grader's.
Ruling (M7): macro pass@k averages each env's own value; an env's pass@k may be over fewer problems (n ≥ k, said in `n_problems`); no macro CI.
Ruling (M8): grading is sequential and its progress in memory; an admin restart loses a running grading, and the next grade call starts it again (manifest last keeps it safe).
Ruling (M9): the platform's `set.json` carries `seed` and `index_range`, so anyone can recompute the source indices; the answers are public in the packages anyway. To revisit if a private source is ever used.

## v2: evaluations generated by SN81 miners

Ruling (user, 2026-10-01): no per-token pricing, no burn change, no pricing route, no `miner_alpha_per_window`, no pace controller. An eval job is paid exactly like a corpus/SFT job: a fixed cap share per task, split by verified tokens, settlement byte-identical to the base. The share defaults to 0.02, is set at job creation by the operator/platform and changed with the existing cap route; the criteria are to be decided with the user later. Per-token pricing is a possible later update. The design's "Incentive logic" section is replaced by a short "Incentives" section.
Ruling: an eval job's prompt source is `eval-set:<set_id>:<n>:<sha256>` — the first n problems of the frozen set, `sha256` over exactly those `prompts.jsonl` lines. No new manifest field is needed, the source is self-checking, and row i of the job is line i of the set, so `prompt_index` maps to `problem_id` through the set's recorded order. Only the model's chat template may render it (`chat-template-v1` / `chat-template-thinking-v1`); the rows are already rendered by the catalog template.
Ruling: validators read an eval job's prompts from the subnet bucket (`publish-set` now also writes `reliquary/eval-sets/{set_id}/prompts.jsonl` there; prompts are not secret), miners from the control serving the job (`GET /corpus/jobs/{job_id}/eval-prompts`, the job's lines byte for byte), both checked against the source's sha256. Consequence: an order's problems become public to every miner; the sets are not secret from SN81 and will be seen by anyone who mines them (re-use of a set across orders leaks it further; rotating sets is a follow-up).
Ruling: the contract of an eval job declares the set's catalog environment (e.g. `reliquary_logic_v2`), while its manifest names the eval-set source; `prepare_corpus_job(contract_environment=...)`.
Ruling: the manifest gains an optional `seed` (non-negative int), written only when present, so every existing manifest is byte-identical; a binary that predates it refuses an eval job's manifest (unknown field), which only the new eval control and new miners serve. Nothing verifies a miner used the seed (TOPLOC does not cover sampling). The admin derives it from the job id when the platform gives none.
Ruling: eval job ids start with `order-eval-` and only eval jobs may: the admin refuses an eval job without the prefix and a non-eval job with it (task id too). The corpus control's hot set ignores every `order-eval-` entry (two processes settling one job would pay its records twice); the eval control serves nothing else.
Ruling: an eval job is declared from a qualification record (`qualification_id`, status `qualified`), not from the admin's qualified-models file: revision, architecture, checkpoint fingerprint, eos and TOPLOC thresholds come from the record the eval control wrote, so the platform never hands the thresholds over itself. The thresholds replace the contract proof's, never under the 60/40/40 floors. `audit_q` is forced to 1.0 (any other value is refused). `prompt_start` must be 0.
Ruling: qualification requests are records in the subnet bucket (`reliquary/eval/qualifications/{id}.json`, `POST/GET /admin/v1/qualifications`), leased by the eval control to an executor registered for that model (`kind: "qualify"` on its claim route). The band is every chunk's measures over the decoded completions; thresholds are `max(p99 × 1.5, floor)` per measure (nearest-rank p99, exp rounded up); the hard ceilings default to four times the floors (240 / 160 / 160, `RELIQUARY_QUALIFY_CEILING_*`); a band over a ceiling, or any honest completion failing its own proofs, refuses the model. `tokens_per_gpu_hour` = completion tokens / decode seconds × 3600 / GPUs, recorded as information only. One executor qualifies (design: +1 during qualification); its provider and host are recorded.
Ruling: the qualification executor decodes with the miners' `VllmGenerator` (same proof capture) and verifies with the auditor's `score_sequences` on the same card after freeing vLLM, so the band is what an honest miner's completion scores at the auditors.
Ruling: the eval control pairs executors on a distinct provider AND a distinct host from every executor already on the batch; an executor registered without both is refused a lease (409 `executor_provider_unknown`). `provider_id`/`host` are optional registry fields, written only when given, so R3's registrations are unchanged.
Ruling: decisions — two scores that agree under R3's `scores_agree` (same per-item decision, every measure within the drift tolerance) decide; otherwise a third executor is leased; whoever agrees with nobody is quarantined (registry status `quarantined`) and its co-signed passes re-audited by fresh pairs (R3's `reaudit_executor`, with every re-audit going to executors, never a GPU here); with no agreement after 5 scorers the batch fails as a validator-side error and is retried by the auditor. There is no local fallback and no recheck sampling: a batch waits for its pair.
Ruling: the eval control's executor routes are `/corpus/internal/eval-audit/{claim,heartbeat,<lease>/result}` — the R3 protocol unchanged (`audit-executor --eval`), plus an optional `kind` on claim (`audit` by default, `qualify`, `any`). nginx routes `^/corpus/jobs/order-eval-` and `^/corpus/internal/eval-audit/` to it (documented in the v2 design). It serves the job-scoped corpus paths only (no legacy `/corpus/job`, `/corpus/submit`), so a miner submits an eval job on `/corpus/jobs/{job_id}/submit` (the miner client does so for an `order-eval-` job).
Ruling: the eval control's settlement is the unchanged `CorpusSettler`; its archives are written only under an `order-eval-` task this process serves (`EvalArchives`), since RELIQUARY_TASK_ID never lists its hot-wired tasks.
Ruling: grading from a job (`source: "job"`) requires the job drained (409 `job_not_drained`) and the request to name exactly the job's set, problem count and samples (`slots_per_prompt × n`), else 422 naming the expected values. Passing, non-voided submissions are numbered as samples in submission-id order per problem; `finish_reason` is `stop` when the completion ends on the job's eos, else `length`. Provenance in that mode: the platform's `model, revision, model_sha, sampling, thinking, max_new_tokens` plus `generation: "sn81-miners"`, `job_id`, `miner_hotkeys`, `audited_fraction`, `verification` (TOPLOC thresholds of the job's contract, `sampling_verified: false`) and the note "sampling not verified"; `vllm_version`, `gpu`, `pod_provider_id` are required only for an uploads grading.
Ruling (dropped with the user's ruling): no `price_per_token`, `miner_alpha_per_window`, pricing route or pace controller; the coordinator's "read miner emission from chain at creation" went with them.

## v2 fix pass (review of the v2 commits)

Ruling (C1, coordinator): qualification needs two executors on distinct providers and hosts (platform-registered `provider_id`/`host`, `scope: "eval"`), measuring apart. Agreement: for each measure, `max(p99) <= 1.5 × min(p99) + slack` (slack 2 exponent mismatches, 1.0 mantissa) and identical checkpoint fingerprints; one side with failing honest proofs is a disagreement, both refuse the model. A disagreeing pair is never paired again; three disagreeing pairs fail the qualification (full refund). The agreed band is the per-measure maximum of the two.
Ruling (C1): thresholds are `max(p99 × 1.5, floor)` clamped to a hard threshold ceiling, `RELIQUARY_QUALIFY_THRESHOLD_CEILING_{EXP,MANT_MEAN,MANT_MEDIAN}`, default 120/80/80 (twice the floors); `clamped` names the measures cut. A model whose agreed honest p99 is itself over the ceiling is refused (its honest work would fail the clamped thresholds). The band ceiling of v2 is gone. `jobs create` and the admin refuse thresholds outside [floor, ceiling].
Ruling (C1): eos and architecture come from the control reading the model's `config.json` and tokenizer files at the pinned revision on CPU (`model_facts`); `QualifyResult` no longer carries them. The checkpoint fingerprint is the only executor-reported model fact, and both qualifiers must report the same one.
Ruling (I4): a qualification record binds model@revision, set, `problems` (= the job's `prompt_count`), sampling `{temperature, top_p, top_k}`, `max_new_tokens`, thinking; job creation refuses any difference (409 `qualification_conditions_differ`) and writes the order's sampling into the manifest (miners are told it; nothing verifies it). `completions` ≤ 64 and `completions × max_new_tokens` ≤ 64 × 32768; every prompt is decoded in one vLLM call (`VllmGenerator.generate_many`); a qualify lease lasts 1800 s + 0.25 s per token of budget; three expired leases fail the qualification.
Ruling (I1): the eval control writes its status every 30 s to `reliquary/eval/control/status.json` (subnet bucket); `GET /admin/v1/eval-control/status` returns it. `executors_needed` for a model = the largest number of scorers a waiting batch needs (2, or 3 after a disagreement) minus the live distinct providers/hosts of that model (live = heard within 90 s, not quarantined, placed), floored at 0.
Ruling (I2): at most 3 scorers per batch. No agreeing pair after 3 → the batch is parked: its records stay pending, are not retried by this process (an operator must act, e.g. after quarantining an executor and restarting), are never counted as validator errors, and the job is flagged `needs_attention` in the status with the reason. A job's auditor or settler failing is logged and flags the job; it never stops the process.
Ruling (I3): a decision is taken only when every agreeing pair holds the same per-item decisions; conflicting agreeing pairs park the batch, with no id-ordered tie-break and no quarantine. Registry entries carry `scope` ("corpus" by default and not written; "eval" requires `provider_id` and `host`); the corpus control refuses `wrong_scope` for eval executors, the eval control for corpus ones, and the eval control's quarantine is `set_executor_status(scope="eval")`, which leaves any other executor untouched. `provider_id`/`host` must be Lium's provider identity and the rental host, set by the platform's fleet, never by the executor.
Ruling (I5): a job grading needs the job drained AND complete (every prompt of the job holds `slots_per_prompt × n` passing, non-voided samples; never true with no submission), else 409 `job_not_complete`, unless the request says `allow_incomplete: true` (the platform, after its deadline): the report then has `complete: false` and `provenance.allow_incomplete: true`.
Ruling (I6): job-mode provenance is built from the manifest (model, revision, checkpoint fingerprint, sampling, thinking from the renderer, `max_new_tokens`, seed, eos), the eval job record (`reliquary/eval/jobs/{job_id}.json`, written once at creation: qualification id, set, problems, samples, conditions) and the qualification record (band, clamped measures, qualifiers' providers/hosts/GPUs). The request's `model, revision, model_sha (= revision), sampling, thinking, max_new_tokens` are only cross-checked: any difference is 422 `provenance_mismatch`.
Ruling (I7/I8): `CorpusJobSet` gains `on_unwired` (and `screen`); the eval control releases a drained job's wiring, pool view and re-audit listeners, its prompts and, when no other job uses the model, its tokenizer. Executor heartbeats are written to the registry at most every 30 s per executor, as the corpus control does.
Ruling (M1/M2): the corpus control refuses an `order-eval-` task at boot (RuntimeError naming the eval control) and screens such entries before any manifest read when hot; the eval control screens non-eval entries the same way.
Ruling (M3): `cap` is required for non-eval jobs (422 `cap_required`); only an eval job defaults to 0.02.
Ruling (M4, left): an eval job left active after its slots fill keeps its cap inside the pool limit until the platform retires it; the platform retires it when the job's status shows every slot full (it must, before grading).
Ruling (M5): the eval control downloads only tokenizer and config files (`*.json`, `*.model`, `*.tiktoken`, `merges.txt`, `vocab.txt`, `*.jinja`) with `token=False`; a gated, missing or private repo is a deterministic refusal (remembered), not a transient retried forever. The vocabulary bound is the config's `vocab_size` (the embedding rows the auditor checks token ids against); the text-equality check covers ids in between.
Ruling (M6): `QualificationQueue` skips terminal records on refresh; a raced result write answers 409 `qualification_changed_retry`; `qualification_id` at job creation is checked against the admin scope.
Ruling (M7/M8/M9/M10): a missing `prompts.jsonl` in the subnet bucket is logged with its key; job records are read 16 at a time; `run_eval_control(refresh_every_seconds)` is used; an eval prompt must be exactly one user turn.
Ruling (M11, left): the qualification executor decodes, frees vLLM and loads the HF model in one process; separate processes are a follow-up once it runs on a GPU (untested here).

## v2 cross-side fix (platform review C1, C2, I4)

Ruling (C1): eval executors, audit and qualify alike, heartbeat on `POST /corpus/internal/eval-audit/heartbeat` with `detail: {"loaded": bool, "leases": int}`; the eval control writes the registry's `last_heartbeat` and `heartbeat: {"leases": int, "loaded": bool}` as the corpus control does — at once when `loaded` or `leases` changed, otherwise at most every 30 s. `leases` defaults to the leases the control holds for it. Every claim and result also counts as contact. `reliquary corpus qualify` heartbeats every 20 s from its first second (download and load included, `loaded: false`), `loaded: true` once the model is loaded, `leases: 1` while a qualification runs.
Ruling (C2): an eval job stays completable. When a submission of an eval job fails its audit (or a pass is voided by a re-audit, or a banned miner's pass is voided), the eval control records it in the job's ledger (`failed: {prompt: [first 12 hex of each submission id]}`, idempotent; written only once a failure exists, so every other ledger is byte-identical); each recorded failure reopens one slot of that prompt, up to `3 × slots_per_prompt` slots in all (`ATTEMPTS_PER_SLOT`). A prompt is `complete` when its slots hold V submissions not known to have failed, `exhausted` when every attempt is used without that; the control reconciles every failing verdict into the ledger when it (re)starts, so a crash between a verdict and its ledger write never leaves a prompt stuck. Old binaries refuse a ledger carrying `failed`, which only the eval control serves. Miners find reopened slots on their own walk (eval jobs are `free` order).
Ruling (C2): an eval job's public status (`GET /corpus/jobs/{job_id}/status`) and the eval control's status (`jobs[job_id]`) gain `prompts_complete`, `prompts_exhausted` and `complete` (every prompt complete or exhausted); `prompts_full` counts prompts with no slot left (capacity included). Grading's completeness uses the same definition with the authoritative counts: a prompt is complete when its passing, non-voided samples reach `samples`, or when the ledger says it is exhausted; exhausted prompts' missing samples are failures in the headline, and the report's provenance names them (`prompts_exhausted`, `exhausted_problem_ids`).
Ruling (I4): the eval job prefix is `${RELIQUARY_ADMIN_TASK_PREFIX}eval-` (`order-eval-` by default). The admin derives it from its own `task_prefix`; the eval control, the corpus control and the grade route from the environment variable, which must match on every process and in the nginx regex. The miner submits on the scoped path because the job's manifest names an eval set, not because of its id.
