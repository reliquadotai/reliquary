# Flexible evaluations on the subnet (operator side)

2026-10-02. Extends `2026-10-01-evaluation-on-subnet-design.md` (v2). Nothing in the
customer flow changes: the platform keeps ordering evaluations from the four held-out
presets. What this adds is the operator's own way in, as flexible as `jobs create`.

## Goal

An operator benchmarks a checkpoint of their choice, on a source of their choice, over
a range of their choice, generated by SN81 miners and graded by the subnet:

```
reliquary eval build-set --source verifiers:aime26 --out sets/aime26
reliquary eval publish-set sets/aime26
reliquary eval create --set aime26 --model ReliquaryForge/Teutonic@<rev> \
    --samples 8 --max-new-tokens 32768 --thinking --temperature 0.6 --top-p 0.95
reliquary eval status --job order-eval-...
reliquary eval grade --job order-eval-... --out results/ck120-aime26
reliquary eval compare results/ck0-aime26 results/ck120-aime26
```

The question it answers is the one a training run asks: did the trained checkpoint get
better than the one it started from, on tasks it did and did not train on.

## Non-goals

- **Multi-turn.** Single-turn only. The set format carries an `interaction` field so the
  next step (catalog `episode` environments, then BFCL through an adapter to the episode
  replay contract) adds rows without changing what exists. A multi-turn row is refused.
- **Customers.** No platform or API change. The platform's orders keep the four presets.
- **Deployment.** Code and tests only. Deploying the order control is a separate step.
- **Reusing another checkpoint's thresholds.** A qualification yields the checkpoint's
  fingerprint as well as its TOPLOC band; a new revision has another fingerprint, and
  taking it from anywhere but a measurement would let a job run on an unchecked model.
  Every checkpoint is qualified, automatically.

## 1. Sets from any source

`reliquary eval build-set` takes a source instead of one of four environments:

| Option | Meaning |
| --- | --- |
| `--source NAME` | A catalog environment (`reliquary_dapo_math_v1`, ...) or `verifiers:<taskset-id>` |
| `--split SPLIT` | Catalog only. Default `train` for the runtime factory, else the package's own split |
| `--start N --count M` | The range `[N, N+M)` of the source. Default: all of it |
| `--sample K --seed S` | Draw K problems from the range with `random.Random(S).sample`; without it the whole range, in order |
| `--taskset-args JSON` | Verifiers only: the taskset config, frozen into the set (e.g. `{"diamond": true}`) |
| `--preset NAME` | The four held-out regions of v2 (`math`, `code`, `logic`, `instruction_following`), as before |

`--preset` keeps the v2 behaviour byte for byte (same set ids, same cards), so the
platform's sets are unchanged. Exactly one of `--preset` and `--source`.

### Training overlap is recorded, never refused

For a catalog source the card's `disjointness` is computed for the chosen range rather
than for a fixed region:
- **RL**: the whole `train` split of every catalog source (unchanged ruling);
- **corpus jobs**: `CORPUS_RANGES`, by source lineage;
- **held-out regions**: whether the range lies inside one of the v2 regions.

The card says, per overlap, which job or RL and which rows. A range that overlaps is
built anyway: measuring on training rows is a legitimate question, and the report
carries the overlap next to the score so nobody can read one without the other.

For a Verifiers source: `{"external_benchmark": true, "note": "not in Reliquary training
data"}`.

### Verifiers sources

`verifiers:<id>` loads the installed taskset with the frozen `--taskset-args`
(`vf.taskset_config_type(id)(id=id, **args)`), iterates its tasks, and keeps each task's
`key` (the taskset's own content address). Refused at build time, with the reason:
- a task with tools (`Task.toolsets(config)` non-empty) — BFCL;
- a prompt that is not text, or a message list other than an optional system turn and
  one user turn;
- a task whose reward may call an LLM judge: its task config holds a `JudgeConfig`
  field or `judges`, and the task's `@vf.reward` methods are not all replaced through
  `task.rewards.<name>.fn`. GPQA becomes buildable by replacing `correct` with
  `reliquary.eval.verifiers_rewards:gpqa_letter`, the upstream letter extractor alone.

The card records the taskset id and args, the distribution version of the taskset's
package and of `verifiers`, and `needs_runtime` (a reward with a required `runtime`
parameter: LiveCodeBench). Verifiers is an optional dependency, imported only here and
in grading.

### Card and rows

`set.json` gains `source_kind` (`catalog` | `verifiers`), `interaction` (`single_turn`),
`selection` (`{start, count, sample, seed}`), and for Verifiers `taskset`. The schema
id stays `reliquary/eval-set/v1`; a v2 card reads as `source_kind: catalog`.

`prompts.jsonl` rows: `{"problem_id", "env", "set_id", "interaction": "single_turn",
"messages": [{"role": "system", ...}?, {"role": "user", ...}]}`. `grading.jsonl` rows:
catalog `{problem_id, source, split, source_index, prompt_sha256}` as today; Verifiers
`{problem_id, source: "verifiers:<id>", task_key, prompt_sha256}`, where `prompt_sha256`
covers the system text and the user text.

## 2. The system turn

The only path from a set row to the model is the chat-template renderer, so the system
turn is carried there and nowhere else:
- `register_eval_prompts` accepts `[user]` or `[system, user]`, text only;
- `EvalSetEnvironment.get_problem` returns `system` beside `prompt` when present;
- `SingleTurnPromptJob.task_for` puts it in `EpisodeTask.metadata["system"]`;
- `ChatTemplatePromptRenderer.initial_text` renders `[system, user]` when the task has
  one, `[user]` otherwise — so every catalog row renders exactly as before;
- qualification hands the system text to its executors, which render it the same way.

Miner, auditor, executors and qualifier all go through `ChatTemplatePromptRenderer`, so
fidelity (`check_prompt_fidelity`) holds by construction. No order job is deployed, so
no running party sees a row it cannot read.

## 3. The contract of an external set's job

A job's contract declares one environment, composed from the catalog; an eval job
declares its set's catalog source. A Verifiers set has none, and the protocol catalog is
pinned by tests to compiled profiles. The job declares `reliquary_external_eval_v1`
instead, a body defined beside the eval code (`answer_format: "text"`, the identity
prompt template, `environment_contract_id: "reliquary/external-eval/v1"`), passed to
`compose_profile` through a new `external_bodies` argument that accepts that one name
only and skips the installed-spec check (there is no package to check it against: the
set's card is the identity). Nothing that runs an order job reads the declared
environment's rows: they come from the set.

## 4. `reliquary eval create`

A client of the admin service (`--admin-url`, default `http://127.0.0.1:8790`, signed
with `RELIQUARY_ADMIN_SECRET`); there is no second write path.

1. Read the set's card from the subnet bucket; `--count` takes its first N problems
   (default: all).
2. Find a qualification with exactly the job's conditions, by id: the id is
   `<task prefix>q-` + the first 40 hex of sha256 over the canonical conditions (model,
   revision, set, problems, sampling, budget, thinking), so asking twice finds the first
   one (the admin bounds ids to its task prefix and 63 characters). Request it
   if absent (`POST /qualifications`), then poll until `qualified` or a terminal failure,
   printing its state.
3. Create the job (`POST /jobs` with `eval_set_id`, `qualification_id`, sampling, budget,
   thinking, samples, cap, seed). The job id defaults to
   `<task prefix>eval-<rev[:8]>-<set>`, shortened with a hash of the rest past 63
   characters (the grade route's bound), and can be given.

`--set` is repeatable: one qualification and one job per set, qualifications requested
together. `reliquary eval status --job ID` prints `GET /jobs/{id}/status`.

The revision must be a full 40-hex commit (the admin refuses anything else);
`--model repo@rev` is split on `@`.

## 5. Grading

`_Graders` gains a second branch, chosen by the grading row's `source`:
- catalog: unchanged;
- `verifiers:<id>`: open the taskset once per set with the card's args, index tasks by
  `key`, refuse a drifted row (`source_drift`, as today) when the task's prompt no longer
  hashes to `prompt_sha256`, build a trace (system, user, the completion's answer text as
  the assistant turn) and await `Task.score`. The answer text is the text after the last
  `</think>` (an unterminated block leaves nothing: a format failure), because a
  Verifiers task reads `last_reply` and would otherwise grade the reasoning. A task
  needing a runtime gets a Docker runtime with every destination denied; a host without
  Docker grades such rows `score = null` with the reason, never 0.

The admin grade route accepts a `job`-source request without `provenance`: the facts
are the job's and its qualification's, as the route already computes them. A new route
`GET /admin/v1/evaluations/{eval_id}/files/{name}` (`report.json`, `manifest.json`,
`graded.parquet`) returns a graded evaluation's files from the deliveries bucket.

`reliquary eval grade --job ID [--out DIR] [--allow-incomplete]` posts the grade request
(the eval id defaults to the job id), polls until done, and writes the three files to
`--out`.

`reliquary eval compare A B` reads two `report.json` and prints, per set and environment,
pass@1 of each, the difference and a paired bootstrap interval over the problems both
graded (2000 resamples, seed 0). It refuses two reports whose conditions differ (set,
samples, sampling, budget, thinking) and says which.

## Testing

- Sets: catalog range/sample/whole-range selection, overlap recorded for RL, corpus and
  held-out regions, presets byte-identical to v2; Verifiers sources through a fake
  taskset module (no network), refusals for tools, multi-message prompts and judges.
- System turn: rendering with and without system through a real tokenizer's template
  stub; fidelity check passes on a system row; qualification lease carries it.
- Contract: an external set's job composes, its contract declares
  `reliquary_external_eval_v1`, the order control serves it, and the cross-side test
  (`test_eval_cross_side.py`) runs once on an external set.
- Grading: a fake Verifiers taskset graded end to end, reasoning stripped, drift refused,
  runtime-less host gives `null`; one test on the real `aime26` taskset when it is
  installed (skipped otherwise).
- CLI: `eval create` against the admin app in process (httpx ASGI transport): request,
  poll, create, idempotent second run; `eval grade` writes the three files; `eval
  compare` refuses differing conditions.
